# Native RetroBat comparison fixture

Status: original fixture prepared and structurally tested; native rendering/navigation and write isolation are not yet verified. Production adapter registry remains empty. This fixture does not activate or install a theme in a real installation.

## Prepare original fixture

Run only this named opt-in test from the repository root:

```powershell
cargo test --locked --manifest-path src-tauri/Cargo.toml theme_studio::export::native_fixture::prepare_native_comparison_fixture -- --ignored --nocapture
```

The test creates a fresh owned system-temporary directory with the RetroDrive-native-fixture- prefix, refuses existing file collisions and prints its location. It does not accept an output path or launch a process. No third-party binary, font, theme, artwork, game or BIOS is copied. Do not run all ignored tests: some unrelated tests access real installations.

Contents:

- source.json: original universal document for system-select/game-list scenes.
- home/.emulationstation/themes/retrodrive-native-check/: actual candidate XML, generated two-color PNG, credits and deterministic file manifest, produced by the real managed-store/compiler/package flow.
- home/.emulationstation/es_settings.cfg: fixture theme, detailed view, no gamelist save on exit.
- home/.emulationstation/es_systems.cfg: one fictional rdtest system, inert .rdtest extension and deliberately unavailable RETRODRIVE_NATIVE_TEST_LAUNCH_DISABLED command.
- home/fixture-games/: two inert text markers and original fictional gamelist metadata.

The temporary fixture's project identity is generated by normal project creation; separate preparations therefore have different canonical source digests. Building twice from identical stored content remains byte-deterministic. All package paths are relative and fixture configuration resolves game paths beneath its home; the printed machine-local preparation path is not committed.

## Isolation evidence and unresolved limits

Pinned official source revision 22d8dfbe44fa324d448fea01b3f6a00b5ae76d68 provides [main.cpp](https://github.com/RetroBat-Official/emulationstation/blob/22d8dfbe44fa324d448fea01b3f6a00b5ae76d68/es-app/src/main.cpp), [Paths.cpp](https://github.com/RetroBat-Official/emulationstation/blob/22d8dfbe44fa324d448fea01b3f6a00b5ae76d68/es-core/src/Paths.cpp), [Settings.cpp](https://github.com/RetroBat-Official/emulationstation/blob/22d8dfbe44fa324d448fea01b3f6a00b5ae76d68/es-core/src/Settings.cpp) and [SystemData.cpp](https://github.com/RetroBat-Official/emulationstation/blob/22d8dfbe44fa324d448fea01b3f6a00b5ae76d68/es-app/src/SystemData.cpp).

The candidate source processes --home before settings initialization, resolves user settings/themes/log paths from that home, and supports --windowed/--resolution/--gamelist-only. It can also consult the executable directory for resources/configuration. A home override is not an OS sandbox, and this pinned source is not yet associated with the exact installed build. Native processes could run scripts or touch other locations. Presence of option strings in a binary is not proof of isolation. Do not claim the installed target is unchanged after a native run without checking its scoped write behavior.

Preparation alone is safe to automate. Actual frontend execution, a visible interactive window and any target-setting changes must be explicitly scoped before running. No native process is launched by the test or ordinary application. The current evidence supports preparing a disposable comparison environment, not unattended launch/activation.

## Native check sequence (pending)

1. Record local frontend identity and source/build association. Keep installation-derived versions/hashes and absolute paths out of the PR unless public disclosure is separately authorized.
2. Review launch isolation and allowed writes. Use the generated home and a temporary working directory, not the active RetroBat launcher. Check fallback config, scripts, logs and environment handling for the exact executable. If isolation cannot be established, use a separately owner-prepared disposable installation or VM before proceeding.
3. On an explicitly scoped launch, request windowed 1280x720, the generated home and gamelist-only mode. Verify the runtime loads the fictional rdtest system and fixture theme; abort if real library/system data appears.
4. System view: inspect the original caption and red/blue image. Enter the game-list view without launching a marker. Move selection between the two fictional entries; verify title and description change with selection, with the static caption unchanged.
5. Compare text position, local bounds, center alignment, font size, clipping and image Fit/letterboxing against the document. Check 1920x1080 and portrait separately. Record mismatches rather than adjusting a golden file to hide them.
6. Back navigation, clean close and repeated launch must work. Verify settings/log/gamelist writes remain inside allowed temporary locations and the installed theme/settings remain unchanged. Capture only original fixture pixels and sanitized log summaries.
7. Record exact pass/fail/not-tested results for each feature. No profile registration based solely on parser success, command-line string presence or an attractive screenshot.

Current result: fixture generation and XML/config structural tests only. Native launch, settings write tracing, screenshots, navigation and real rendering are pending. Runtime quirks must feed compiler diagnostics or explicit fallbacks, never silent source loss. User-facing export, source archives and deployment remain separately scoped.
